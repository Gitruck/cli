## 一、两个数不是一回事

| | 公式 | 低估语速的后果 | 保守方向 |
|---|---|---|---|
| **计费折算**（`_SPEECH_CHARS_PER_MINUTE = 240`） | 计费分钟 = 字数 ÷ 语速 | 分钟数变大 ⇒ **多收** | 低估是**安全**的（不少收） |
| **写稿折算**（挂钟语速，本文件） | 成片时长 = 字数 ÷ 语速 | 时长被高估 ⇒ **稿子写短** | 低估是**有害**的（成片缩水） |

240 的来历：volc 引擎**单点实测 100 汉字 ≈ 23.06 秒（约 260 字/分钟），再人为下调留余量**取 240；
2026-08-20 起它**已退出计费链路**，保留只为时长预估。把这份「宁可低估」的偏置搬到写稿侧，
就是本档案要治的那个缺陷 —— 按 240 写 3 分钟稿 = 720 字，用 `narrator` 349.3 的挂钟语速实播只有
**2.06 分钟，缩水 31%**。

两条口径的换算关系：**挂钟语速 = 有效语速 × (1 − 停顿占比)**。
注册表 `acoustic.rate` 记的是**有效语速**（扣掉停顿的净说话速度），写稿要的是**挂钟**（含停顿）。

## 二、标定方法（一条记录 MUST 齐备五项，缺一不得作口径依据）

| # | 必填项 | 说明 |
|---|---|---|
| ① | **音色与引擎** | `voice_id` + `engine`（自训 gpt_sovits / 云引擎 volc / …） |
| ② | **影响语速的合成参数** | `speed`、`fragment_interval`、`split_method` 等。`narrator` 的 `fragment_interval=0.28` 会实打实抬高句间停顿占比，不记就没法复现 |
| ③ | **稿件** | 字数口径（Unicode 码点、含不含标点与英文数字，与服务端 `_MAX_TEXT_LEN` 同口径）+ 稿件出处或哈希 + 字数 |
| ④ | **测量方法** | 音频总时长怎么取（`ffprobe` duration）、首尾静音算不算 |
| ⑤ | **结果两个数 + 样本数 + 日期** | **挂钟语速**（写稿用）与**有效语速 / 停顿占比**（注册表口径），样本条数，标定日期 |

两条禁令：

- **MUST NOT 再写「（TTS 实测）」这类无主体、无出处的括注**。任何写进图纸的语速数字，
  要么能指到一条满足上表的档案，要么明确标注为「派生值 / 缺省值」。
  （这条的由来：`SKILL.md` 的「200-240 字/分钟（TTS 实测，语速快的音色偏 270）」是
  **一次性写入、无出处**——`git log -S` 只命中 skill 首发那一个 commit，归档 change 里 grep 零命中。）
- **单点标定 MUST NOT 外推到其它引擎的音色**。240 那次是 volc 单点标定，与自训 gpt_sovits 的
  `narrator` 没有任何关系。

**这条记录的价值不在它自己，在它顺手验了 §3.2 那张派生表。**
注册表给这条音色 `rate=321.77 / pause=0.31`，按 `挂钟 = rate × (1 − pause)` 派生得 **222.0**；
两次实测 214.3 / 218.4，偏 **−3.5% / −1.6%**。
§3.2 的 49 条派生值此前**从未被任何实测检验过**（3.1 是注册表自身口径的复算，不是独立测量），

仍 MUST NOT 宣称全库已标定，但对**云引擎 volc 这一档**，派生值可以当估值用，误差量级 <5%。

⚠️ 另记一条选音色时该知道的事实：这条音色的 `pause=0.31` 是**全库最高**，挂钟 222.0 正是 §3.2 那张表的
`min` 值本人。同一份稿子交给它，比交给缺省 330 长 **48%**，比交给 `narrator`（349.3）长 **57%**。
写稿时 MUST 按它自己的挂钟值反推字数，照缺省 330 写会让成片直接长出三成。

| 项 | 值 |
|---|---|
| ① 音色 / 引擎 | `narrator` / 自训 gpt_sovits（生产环境 2026-09-16，CLI 1.1.7 `gtrk tool audio_tts_clone --speaker narrator`） |
| ② 合成参数 | `speed` 未传（= 1.0）；`fragment_interval` 样本 a 未传（跟随音色预设 **0.28**）、样本 b 显式 `--fragment-interval 0.2`；`split_method` 走服务端默认 |
| ③ 稿件 | 同一稿两跑，Unicode 码点口径（含标点）**261** 码点，黄石公园解说短稿 `sha256:a1d8eda9b2e44c40…`（正文与产物在工作区根 `_evidence/tts_pause_2026-09-16/`） |
| ④ 测量 | wav 总时长 = 采样数 ÷ 采样率，**首尾静音计入**；停顿占比按 infra `add-tts-fragment-interval-param` 5.1 法（0.1 s 窗 RMS < 2% 峰值、连续 ≥0.2 s 计一段） |
| ⑤ 结果 | 样本 a：261 / 44.60 s = **351.1 字/分**，停顿占比 7.0% ⇒ 有效 ≈ 377.5；样本 b：261 / 43.80 s = **357.5 字/分**，停顿占比 4.3% ⇒ 有效 ≈ 373.6。样本 2 条（同稿两参数），日期 2026-09-16；任务 114462641666715654 / 114462754220863494 |

**这条记录的价值同 §3.4：拿真机音频去撞注册表口径，这次撞的是自训那一档。**
catalog 给 `narrator` 的派生挂钟是 349.3（`rate=379.7 × (1 − 0.08)`），样本 a 实测 351.1，偏 **+0.5%**；
有效语速 377.5 对注册表 379.7，偏 **−0.6%**。§3.2 那张派生表此前只有 volc 一个实测锚点（§3.4），
现在自训引擎也有了一个，两档都落在 5% 内。仍 MUST NOT 外推到其它自训音色（各自 `pause` 不同）；
也要记住本稿只有 45 s，短稿的停顿占比对首尾静音更敏感，长稿回校（§五）攒到第三条再谈收敛。

⚠️ 顺手得到的一个事实：`fragment_interval` 从预设 0.28 压到 0.2，挂钟语速只快 **1.8%**（44.6 → 43.8 s）。
写稿折算时这档参数可以忽略；它改的是听感（静音总量 −38%），拿它去「调时长」没有意义。

## 四、缺省值 330 是怎么来的，用在哪儿

- **取值**：落在全库挂钟中位 **308.7** 与 `narrator` **349.3** 之间，覆盖真机 **316–342** 区间的中部；
- **性质**：**缺省估值，不是任何一条音色的实测值**。用它折算时 SHALL 在交付说明里明示这一点；
- **适用边界**：只适用**中文**、**正常语速档**、**未加 `--speed`** 的合成。
  换引擎、换语种、动了 `--speed` / `fragment_interval` 的，一律回 §二 重新标定，MUST NOT 沿用；
- **怎么退役**：终局 (C) 上线（catalog 投影出 `acoustic` 或派生只读字段）后，
  取值路径改为「读 catalog 字段」，330 只在字段缺失时兜底。

## 五、回校怎么攒样本（`SKILL.md` §五 ④′）

TTS 合成完成后，稿件字数与音频实际时长都已在手（`project init --tts-task` 本就要读它）：

1. 算 **实测挂钟语速 = 稿件字数 ÷ 音频实际时长**；
2. 与写稿所用估值比对，**偏差 >15% 在交付汇报里点名**（报「估 X / 实测 Y / 偏 Z%」）；
3. 按 §二 五项格式**追加一条**进 §三 —— 每跑一条片就攒一条样本，「孤证」这个病从结构上被治掉；
4. **MUST NOT 自动改稿、MUST NOT 自动重跑 TTS**：改稿要从配音步重跑、重付 TTS 费用，返工与否由用户拍板。
